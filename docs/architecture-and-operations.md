# معماری و عملیات سامانه

تاریخ بازبینی: ۲۰۲۶/۰۹/۲۵. نوع شواهد این سند: خواندن فایل‌های مخزن؛ نه بازرسی زنده PostgreSQL، Docker، منابع میزبان یا اجرای health. [شروع پروژه](../START_HERE.md)، [حاکمیت](project-governance/) و [وضعیت آزمون](verification-and-known-issues.md) مکمل این سندند.

## مسیر واقعی اجرا

[package.json](../package.json) از React 19، React Router 7، Vite 6، Express 4، pg 8 و TypeScript استفاده می‌کند. نسخه‌های ذکرشده خانواده وابستگی‌ها هستند؛ نسخه دقیق نصب‌شده تابع lockfile و نصب محیط است.

[server/main.ts](../server/main.ts) ورودی backend است. در توسعه، Vite به‌صورت middleware در Express اجرا می‌شود؛ در production همان فرایند API و فایل‌های dist و fallback برنامه تک‌صفحه‌ای را سرو می‌کند. مسیرهای صفحه در [App.tsx](../src/app/App.tsx) و اتصال API در [server/app.ts](../server/app.ts) مشخص‌اند. وجود نمونه‌ها یا فایل‌های قدیمی مخزن به‌تنهایی نشان‌دهنده runtime فعال نیست.

| مسیر | رفتار اثبات‌شده از کد |
| --- | --- |
| npm run dev | اجرای tsx watch روی server/main.ts؛ پیش‌فرض config برابر ۳۰۰۰ مگر PORT تعیین شود |
| npm run build | ساخت frontend با Vite، بسته‌بندی backend به dist/server.cjs و کپی دارایی‌های runtime |
| npm start | [start-production.mjs](../scripts/start-production.mjs)، NODE_ENV=production و PORT پیش‌فرض ۵۰۰۰ |
| شروع backend | migration، ساخت پوشه‌های داده، listen روی 0.0.0.0 و شروع زمان‌بندی backup |
| توقف کنترل‌شده | توقف scheduler، بستن HTTP، پشتیبان هنگام خروج طبق تنظیم و pool.end؛ مهلت نهایی ۱۲۰ ثانیه |

اسکریپت build وابستگی‌های Node را external نگه می‌دارد؛ تنها کپی dist بدون وابستگی‌های لازم نصب کامل نیست. [copy-runtime-assets.mjs](../scripts/copy-runtime-assets.mjs) و فایل‌های migration باید همراه نسخه هماهنگ باشند. restart با نسخه قدیمی dist تغییر source را منتشر نمی‌کند.

## تنظیم اتصال، شبکه و نام میزبان

[config.ts](../server/config.ts) با dotenv/config متغیرهای محیط را می‌خواند. DATABASE_URL اجباری است. فایل env و متغیرهای فرایند باید تحت مدیریت نصب و خارج از گزارش عمومی باشند. مسیر اجرا مهم است: فایل env پیش‌فرض و مسیرهای نسبی به محل اجرای فرایند وابسته‌اند.

DATABASE_SSL در صورت فعال‌شدن، اعتبار گواهی را بررسی می‌کند؛ TRUST_PROXY و COOKIE_SECURE باید با استقرار واقعی تطبیق داده شوند، نه برای رفع خطا کورکورانه فعال شوند. گوش‌دادن روی همه رابط‌ها به‌تنهایی اجازه عبور از فایروال یا امنیت شبکه ایجاد نمی‌کند.

| وضعیت | نمونه و نتیجه |
| --- | --- |
| مستقل از نام Windows | اتصال معتبر به localhost/127.0.0.1 روی همان میزبان؛ تغییر نام رایانه معمولاً نام مقصد را عوض نمی‌کند |
| وابسته مشروط | نام کانتینر در شبکه Docker، IP رزروشده، DNS، مسیر UNC و حساب سرویس؛ باید از محیط همان فرایند قابل دسترسی باشند |
| وابسته مستقیم/پرخطر | DATABASE_URL یا مسیر ذخیره‌سازی حاوی نام قدیمی رایانه؛ نیازمند بررسی DNS، مجوز مسیر و تنظیم اجرای سرویس |

نام diaco-postgres که در گزارش‌های قبلی آمده، شاهد تاریخی نصب است؛ نه فرض عمومی برای hostname یا نام کانتینر همه نصب‌ها. در فهرست فایل‌های ردیابی‌شده بررسی‌شده compose/Dockerfile برای بازسازی قطعی استقرار پیدا نشد. نباید از نبود آن نتیجه گرفت Docker در میزبان استفاده نمی‌شود. در کدهای تنظیم/اجرای بررسی‌شده وابستگی مستقیم به نام رایانه اثبات نشد؛ مقادیر واقعی env، volume، task/service و مسیر شبکه همچنان باید توسط مسئول نصب بررسی شوند.

## اتصال‌ها و ظرفیت

[pool.ts](../server/db/pool.ts) pool با max=20 برای هر فرایند Node، timeout اتصال ۵ ثانیه و بستن اتصال بی‌کار پس از ۳۰ ثانیه دارد. تراکنش‌ها BEGIN/COMMIT/ROLLBACK و آزادسازی client دارند. بیست اتصال بین درخواست‌ها به اشتراک گذاشته می‌شود، نه اینکه هر کاربر یک اتصال دائمی بگیرد.

[auth/routes.ts](../server/modules/auth/routes.ts) و [session-policy.ts](../server/modules/auth/session-policy.ts) سیاست نشست و قفل ورود را اجرا می‌کنند. محدودیت بی‌کاری و انقضای نشست با سقف تعداد کاربران یکی نیست. در بررسی مسیرهای حاضر سقف سخت ۲۰ کاربر یا سقف ثابت نشست برای هر کاربر اثبات نشد. قفل تلاش ورود نیز معادل rate-limit عمومی همه APIها نیست.

max_connections واقعی PostgreSQL، اتصال‌های رزروشده و مصرف سایر برنامه‌ها در این مأموریت پرس‌وجو نشده‌اند. عدد تاریخی ۱۰۰ را تنظیم تضمین‌شده نصب فعلی ندانید. چند فرایند Node مصرف بالقوه pool را چند برابر می‌کند.

برای ۵ و ۱۰ کاربر کار سبک، ۲۰ کاربر ترکیبی، و ۵۰ یا ۱۰۰ کاربر پرتراکنش، هیچ عدد قطعی پذیرش/رد نداریم. افزایش هم‌زمان گزارش‌های سنگین، ثبت فاکتور، heartbeat، آپلود و backup می‌تواند صف pool، قفل رکورد، CPU، RAM یا دیسک را گلوگاه کند. آزمون لازم در محیط جدا: مراحل ۵/۱۰/۲۰/۵۰/۱۰۰ کاربر با مکث انسانی و سناریوی واقعی؛ سنجش p95/p99، خطا، صف اتصال، قفل‌ها و صحت موجودی/تراز. هیچ تضمین «تا ۲۰ نفر» در این سند داده نمی‌شود.

## migration و بازیابی مدیریتی

[migrate.ts](../server/db/migrate.ts) فایل‌های SQL را مرتب می‌خواند، با advisory lock اجرای هم‌زمان را کنترل و checksum را در schema_migrations ثبت می‌کند. مسیر production برابر dist/migrations و مسیر توسعه server/db/migrations است. SQL هر migration معوق در تراکنش اجرا می‌شود. اختلاف checksum migration اعمال‌شده موجب توقف راه‌اندازی است؛ راه‌حل عادی تغییر سابقه یا حذف checksum نیست، بلکه migration اصلاحی جدید پس از بررسی است.

راه‌اندازی سرور یک بررسی فقط‌خواندنی نیست: ممکن است schema و پوشه‌ها و backup را تغییر دهد. پیش از انتشار، نسخه برنامه، migrationها، تنظیمات معتبر، پشتیبان و روش بازگشت باید هماهنگ باشند.

[recovery/main.ts](../server/recovery/main.ts)، [recovery/launch.ts](../server/recovery/launch.ts) و [recovery/service.ts](../server/recovery/service.ts) مسیر بازیابی محلی را تعریف می‌کنند. npm run recovery به source، tsx و تنظیم معتبر اتصال نیاز دارد؛ مسیر محلی با کنترل دسترسی سیستم‌عامل را با API عمومی تغییر رمز یکی ندانید. دسترسی administrator ویندوز، محدودیت loopback و اعتبار کوتاه‌مدت مسیر بازیابی باید در استقرار حفظ شوند. این ابزار اثبات حفاظت کامل مالک در تمام routeها نیست؛ [قاعده مالک](users-and-fiscal-years-guide.md) را ببینید.

## پشتیبان و ذخیره‌سازی ماندگار

مرجع: [backup/service.ts](../server/modules/backup/service.ts)، [scheduler.ts](../server/modules/backup/scheduler.ts)، [routes.ts](../server/modules/backup/routes.ts) و [config.ts](../server/config.ts).

- مسیرهای پیش‌فرض uploads و backup به‌ترتیب data/uploads و data/backups، نسبت به working directory هستند. در جابه‌جایی یا Docker باید روی فضای ماندگار و با مجوز مناسب نگهداری شوند.
- کلید BACKUP_ENCRYPTION_KEY باید Base64ِ ۳۲ بایت باشد؛ رمزنگاری AES-256-GCM است. کلید را جدا و امن نگهدارید؛ داشتن فایل رمز‌شده بدون کلید برنامه بازیابی نیست.
- نام فایل شامل شرکت، نسخه، شناسه نصب، تاریخ/ساعت شمسی و شمارنده V است و به dump.enc ختم می‌شود. تغییر نام فایل جایگزین مدیریت هویت نصب نیست.
- ابزار محلی pg_dump لازم است؛ PG_DUMP_PATH و PG_RESTORE_PATH قابل تنظیم‌اند. خطای تاریخی ENOENT یعنی ابزار پیدا نشده، نه اثبات خرابی دیتابیس.
- fallback Docker تنها در مسیر خطای نبود ابزار و با BACKUP_DOCKER_CONTAINER معتبر فعال می‌شود. مقصد dump داخل کانتینر باید واقعاً همان دیتابیس برنامه باشد؛ نام مشابه کافی نیست.
- «اعتبارسنجی» شامل کنترل فایل، رمزگشایی و pg_restore --list است؛ بازیابی کامل آزمایشی و آزمون کاربردی روی دیتابیس جدا نیست.
- dump دیتابیس به‌تنهایی تضمین پوشش فایل‌های uploads نیست. فایل‌های پیوست، لوگو، تنظیمات اجرای سرویس و کلید رمزنگاری نیز در طرح تداوم خدمت پوشش داده شوند.
- مسیر خارجی ذخیره‌شده، mount، فضای آزاد و مجوز نوشتن باید واقعی باشند. مسیرهای مطلق قدیمی با انتقال نصب خودبه‌خود اصلاح نمی‌شوند.
- scheduler و backup هنگام خروج به خاموش‌شدن سالم وابسته‌اند؛ قطع برق یا kill تضمین پشتیبان نهایی ندارد. «اعتبارسنجی backup» نیز سابقه اجرا ثبت می‌کند و عملیات صرفاً خواندنی نیست.

بازیابی عملی باید ابتدا روی محیط ایزوله، با نسخه سازگار PostgreSQL، کلید صحیح و فایل‌های پیوست آزموده شود. برای رفع اتصال، داده واقعی را حذف یا تنظیمات حساس را از روی حدس بازسازی نکنید.
